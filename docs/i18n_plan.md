# i18n / 雙語系導入評估與規劃

## 目標

為系統新增英文語系，並依照人員在後台設定的語系偏好，於登入後自動切換顯示語言。

## 需求摘要

1. 系統需支援至少兩種語系：`zh-TW`、`en`
2. 使用者可由後台管理介面設定語系偏好
3. 使用者登入後，系統依偏好語系自動切換
4. 模板、提示訊息、前端按鈕文字、日期與數字格式需跟隨語系變化
5. 後續新功能需沿用同一套多語系機制，避免再次硬編碼文字

## 現況評估

目前專案尚未建立正式的 i18n 基礎設施，主要現況如下：

1. `User` 模型沒有語系偏好欄位
2. 登入流程未將語系寫入 session 或 request context
3. `base.html` 與多數模板直接寫死中文內容
4. 前端 JavaScript 中有多處 `zh-TW` 的日期、數字與排序 locale 硬編碼
5. 專案尚未使用 `Flask-Babel` 或其他現成 i18n 套件

這表示雙語系不是只翻幾個字，而是需要先建立可維護的多語系架構。

## i18n 基礎是什麼

i18n（internationalization）是多語系網站的基礎架構，目的不是單次翻譯，而是讓系統具備以下能力：

1. 能知道目前應該顯示哪個語言
2. 能透過統一機制取得翻譯文字
3. 能讓日期、數字、排序、提示訊息依語系變化
4. 能讓未來新增頁面時繼續沿用同一套規則

## 建議架構

### 1. 資料層

在 `users` 表新增語系欄位，例如：

- `preferred_locale`：字串，預設值 `zh-TW`

建議可接受值：

- `zh-TW`
- `en`

### 2. 登入與請求層

登入成功後，系統應從目前登入使用者讀取 `preferred_locale`，並在每次 request 建立目前語系，例如：

- session 中保存 `preferred_locale`
- `before_request` 設定 `g.current_locale`
- `context_processor` 將 `current_locale` 注入模板

### 3. 翻譯資源層

不要在模板或 JS 直接寫中文，應改成翻譯鍵，例如：

- `nav.home`
- `auth.login`
- `user.manage`
- `inventory.title`

再由語系檔對應實際文字。

### 4. 前端格式化層

將以下行為改為依語系動態處理：

- `toLocaleDateString('zh-TW')`
- `toLocaleString('zh-TW')`
- `localeCompare(..., 'zh-Hant')`

應統一改為使用系統目前語系，例如：

- `window.appLocale`
- `document.documentElement.lang`
- 共用 `formatDate` / `formatNumber` / `compareText` helper

## 推薦實作方案

### 方案 A：Flask-Babel 標準方案

適合：

- 預期未來頁面很多
- 希望使用較標準、可持續擴充的做法
- 願意導入套件與翻譯流程

優點：

1. 架構標準
2. 後端模板整合成熟
3. 可支援日期、數字等本地化能力

缺點：

1. 導入成本較高
2. 前端 JS 仍需搭配自己的翻譯輸出機制

### 方案 B：輕量 dictionary / JSON 方案

適合：

- 先求可用
- 專案以 Flask + 原生 JS 為主
- 希望先快速建立雙語能力

優點：

1. 導入速度快
2. 易於控制
3. 後端與前端都能共用較直觀的翻譯資料

缺點：

1. 需自行維護翻譯讀取邏輯
2. 本地化能力需自己補齊

### 建議

以此專案現況，建議先採用「輕量 dictionary / JSON 方案」建立第一版 i18n 基礎，再視需求升級為更完整的 Babel 架構。

原因：

1. 專案已有大量原生 JS 與模板硬編碼
2. 先建立可用的共用翻譯層，比一次全面導入 Babel 更務實
3. 可先完成登入後自動切語系，再逐頁擴充

## 建議第一階段範圍

第一階段不要一次全站翻完，建議先做核心共用層與主要頁面：

1. `base.html` 導覽列與共用文字
2. 登入頁 / 登出流程 / 修改密碼頁
3. 使用者管理頁，加入語系設定欄位
4. 首頁 Dashboard
5. 庫存管理相關共用元件
6. 常用報表頁與週期訂單主流程

## 預估實作步驟

### Phase 1：建立基礎設施

1. User 增加 `preferred_locale`
2. 建立 migration
3. 登入流程接入語系
4. 建立後端 `current_locale`
5. 建立前端共用 i18n helper
6. 建立 `zh-TW` / `en` 翻譯檔

### Phase 2：管理後台接入語系設定

1. 使用者管理頁新增語系欄位
2. 新增使用者 / 編輯使用者 API 支援 `preferred_locale`
3. 顯示目前語系

### Phase 3：共用版面雙語化

1. `base.html`
2. 共用 flash 訊息
3. 共用按鈕 / navbar / footer
4. `html lang` 動態化

### Phase 4：主要功能頁逐步雙語化

1. auth 頁面
2. inventory 頁面
3. weekly order 頁面
4. reports 頁面

### Phase 5：格式化與前端硬編碼清理

1. 日期格式依語系切換
2. 數字格式依語系切換
3. JS alert / confirm / placeholder / title 改由翻譯鍵提供
4. localeCompare 改為使用目前語系

## 風險與注意事項

1. 前端 JS 中有大量中文字與 `zh-TW` locale 硬編碼
2. 一次全站翻譯風險高，容易造成文案不一致
3. 若沒有建立統一翻譯鍵規範，後續維護成本會持續上升
4. 若同時修改大量模板與 JS，回歸測試成本不低

## 建議做法

採分階段導入：

1. 先完成語系欄位與登入自動切換
2. 再完成共用 layout 與使用者管理
3. 最後逐頁納入雙語

這樣可以先讓系統具備真正的多語系能力，再逐步擴大覆蓋範圍，避免一次性重構過大。

## 結論

此功能可行，但屬於中型架構調整，不建議用零散 if/else 或單頁硬翻方式處理。

正確作法是先建立 i18n 基礎，再將使用者語系偏好、登入自動切換、模板翻譯與前端 locale 格式化整合進同一套機制。
